# judge-loop

Параллельный конвейер агентов с двойным гейтом: **детерминированные тесты + кросс-вендорный LLM-судья**.

Демо для показа рабочего сетапа: несколько моделей разных вендоров одновременно решают одну задачу, а результат проходит через два независимых фильтра. В прод попадает только то, что прошло оба.

## Зачем это

Агент генерирует код быстро, но ошибается тихо. Один LLM-ревьюер — плохая защита: модели одного вендора ошибаются похоже (общий стиль, общие слепые зоны), поэтому «свой» судья склонен одобрять «своего» воркера.

Здесь два независимых гейта:

1. **Тесты (объективно).** Сгенерированный код кладётся в изолированную директорию и прогоняется настоящим pytest. Проходит или нет — без интерпретаций.
2. **Судья (субъективно).** Модель **другого вендора** оценивает то, чего нет в тестах: читаемость, обработку непокрытых краевых случаев, риски в проде.

Правило: **воркер и судья никогда не одного вендора.** Это зашито в `core/config.py:judge_for()` и проверяется в каждом прогоне.

## Что показывает

- N задач × M моделей-воркеров — параллельно
- Для каждой пары: сколько тестов прошло, балл судьи, вердикт гейта
- Причина отказа с конкретной строкой ассерта
- Стоимость и время прогона
- Сводку по воркерам: у какой модели какой процент прохождения

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env        # вписать OPENROUTER_API_KEY
.venv/bin/python demo.py
```

Опции:

```bash
.venv/bin/python demo.py --workers 3            # только 3 модели (быстрее)
.venv/bin/python demo.py --tasks t01_slugify    # одна задача
.venv/bin/python demo.py --jobs 12              # больше параллелизма
```

## Структура

```
core/
  config.py    реестр моделей по вендорам + цены + правило кросс-вендорности
  llm.py       единый клиент (OpenRouter), считает токены/деньги/латентность
  verifier.py  прогон pytest в изоляции: свой процесс, таймаут, без сети
  judge.py     судья со строгим JSON-контрактом и порогом баллов
  runner.py    оркестратор: пары (задача × воркер) через ThreadPoolExecutor
  report.py    таблица в терминал + JSON-артефакты
tasks/         спецификации задач с критериями приёмки
tests/         исполняемые тесты (тот самый объективный гейт)
artifacts/     результаты прогонов
demo.py        точка входа
```

## Два неочевидных решения

**Порог важнее вердикта модели.** Судья просят вернуть и `verdict`, и баллы по трём осям. Если модель написала `approve`, но средний балл ниже порога (3.5) — гейт считает это отказом (`core/judge.py`). Модели склонны к вежливому одобрению; баллы честнее.

**Тесты должны быть проверены не меньше кода.** Реальный случай из разработки этого демо: в тесте `parse_duration('30m2h')` ожидалось `7380` вместо `9000`. Все пять моделей ответили верно и «провалили» тест. Если тест врёт, гейт блокирует правильные решения — и это хуже, чем пропущенная ошибка, потому что выглядит как работающая защита.

## Что демо НЕ показывает

Честные границы, чтобы не переоценить:

- **Задачи маленькие и с готовыми тестами.** В реальной работе тесты пишутся вместе со спекой, и это дороже самой генерации.
- **Судья иногда ошибается в обе стороны** — в прогоне есть кейс, где тесты 8/8 зелёные, а судья отклонил по причине, которая в тестах как раз покрыта. Поэтому расхождения судьи и тестов — это очередь на человеческое ревью, а не автоматический вердикт.
- **Нет состояния и памяти между прогонами** — каждый вызов независим.
- **Один файл на задачу.** Реальный PR — это несколько файлов, миграции, конфиги.
